# 员工职业发展地图

古茗营运、营拓、拓展三条序列的职业发展演示。员工能看见自己现在的岗位、下一步能去哪里、差哪些技能，以及提报晋升前要满足哪些条件。页面是中文纯前端，没有后端、登录、正式审批或真实员工数据。所有修改都写在当前浏览器里。

仓库：<https://github.com/Anti0323/career-map-demo>

## 页面

顶栏有五个入口。窄屏底部是「首页 / 岗位 / 技能 / 目录 / 更多」。

| 页面 | 做什么 |
| --- | --- |
| 首页 | 三条序列按 L1–L12 铺开。当前岗位、此刻可探索的岗位、其余岗位用不同标记区分。点「定位我的岗位」会滚到自己所在的格子。点任意岗位进入岗位地图。 |
| 岗位地图 | 左边是当前职责，右边是可晋升或可转营拓的岗位转盘。选中目标后，下方给出岗位画像、能力图、晋升提报条件和技能进化。 |
| 我的技能 | 按「准备学习 / 认证进行中 / 已经掌握」看个人档案，可切换看板和列表。岗位变化后，认证和学习记录仍留在这位员工名下。 |
| 营拓技能 | 全部技能目录。可按类别、学习状态和关键词筛选，加入学习清单，或申请提前认证。目标岗位新增、当前序列还不能考核的技能会单独标出。 |
| 演示数据 | 改这位虚拟员工的岗位、任职日期、认证、课程完成情况和业务达标状态，并预览下一步硬性条件过了几项。 |

页脚标明这是体验版，只供原型评审。

## 本地启动

需要 Node.js 22 或更新版本。测试用 Node 自带的测试运行器直接跑 TypeScript。

```bash
npm install
npm run dev
```

开发预览固定在 `http://localhost:26012/`，端口被占用时不会自动换端口。

```bash
npm test          # 比较、路径、晋升标准、技能代码和演示就绪逻辑
npm run build     # 类型检查后做生产构建，产物在 dist/
```

## 一次完整的演示路径

1. 在首页或岗位地图切换虚拟员工。默认每位员工占一个真实岗位，姓名形如「林xx」，技能按该岗位应掌握的代码预置为已认证。
2. 在岗位地图选一个更高职级或转营拓岗位，设为发展目标。同一时间只能有一个发展目标；换目标时会先确认，收藏和学习计划保留。
3. 看能力图和「技能进化」。左边是当前岗位里衔接的上一项，右边是目标岗位新增的技能。当前岗位还没有这条技能时，标成「需要学习新技能」。
4. 在晋升提报条件里点「开始评估」。条件逐条核验任职时长、课程或认证、业务结果。负责人评估项不会被演示数据自动判过。
5. 硬性条件都满足后，先把该岗位设为发展目标，再确认提报。同一员工同时只能有一条提报。提报后可查看考察流程：负责人评估、必要时的前置技能、能力验证、相关部门审核、晋升通过。
6. 想改结果，去「演示数据」改任职日期、认证或达标状态，再回岗位地图重新评估。也可恢复单名员工或重置全部演示数据。

「一键满足」只作用于当前这一次条件展示，方便评审看通过后的界面，不改员工档案。

## 职业路径

规则在 `src/career-focus.ts`，对照表在 `可晋升岗位.md`。

岗位分成三类角色：区经理以下、区经理、大区经理。各序列的起始职级不同。

| 角色 | 营运 | 营拓 | 拓展 |
| --- | --- | --- | --- |
| 区经理以下 | L1 | L3 | L5 |
| 区经理 | L5 | L7 | L6 |
| 大区经理 | L8 | L10 | L9 |

- 同一角色内，同序列可晋升 1–2 级。
- 跨入下一类角色时，只能进入该类的第一级。
- 营运、拓展可以转入营拓，且不跨角色大类。营拓不再转出。
- 另有三条明确允许的跨档：营运 L5→营拓 L6、营运 L8→营拓 L9、拓展 L8→营拓 L10。营运 L9→营拓 L11 不开放。
- L10 及以上不进入本系统晋升。营拓 L10 仍保留晋升考察。超范围岗位提示联系分公司负责人和总部。

首页格子上的「可探索」和转盘里出现的岗位，都来自同一套 `canDevelopTo`。不在范围内的岗位仍可从首页点开查看职责，但不会出现在晋升路径里。

## 技能

21 项编码技能，定义、课程和认证方式在 `src/source-data.json`，岗位应掌握的代码在 `src/position-skill-codes.ts`，全文对照在 `position-skill-codes.md`。

| 前缀 | 维度 | 阶梯 |
| --- | --- | --- |
| Y | 门店营运 | Y1、Y2、Y3、Y4-1、Y4-2、Y4-3、Y5 |
| S | 加盟商发展 | S1、S3、S4-1、S4-2、S4-3、S5 |
| T | 点位拓展 | T1、T2、T3、T4、T5、T6 |
| M | 团队管理 | M1、M2 |

同一序列里，低职级已经列入的代码会一直保留。更高职级没有新的技能矩阵时，沿用这条序列已有的全部代码。营运序列不设拓展技能，拓展序列不设营运技能。见习营运储干还没有进入 Y1。

团队管理按序列起算：营运 L5 起有 M1、L7 起有 M2；营拓 L6 起有 M1、L8 起有 M2；拓展 L6 起有 M1、L8 起有 M2。M1、M2 不进入能力图的三个轴。

能力图（`src/ability.ts`、`src/AbilityRadar.tsx`）只画营运、加盟商发展、拓展三轴。绿色是员工已认证点数，金色是当前浏览岗位的目标点数。它用来对照差距，不表示晋升或转岗资格。岗位没有可对应技能时，不画目标轮廓。

软性素质写成岗位介绍里的一段话，不进入认证、差距、技能进化或学习清单。

技能有三种开放方式：

- 当前岗位或目标岗位的理论代码里有它：可以走课程、评估和演示认证。
- 拓展侧标明「技能认证与晋升考察同步进行」：课程标成已完成后即可提报，认证留在考察里做。
- 代码还没开放到当前序列：目录里标「仅课程」，达到对应职级后才能考核。

认证层次只在原文把「提出判断 / 独立完成 / 能带教」写成同一套定义时才可比。当前导入的岗位要求里，这三档没有被当成可比较层次，界面显示原文要求。

## 晋升提报

提报条件、考察步骤和通过标准写在 `src/promotion-standards.ts`，阅读版在 `晋升条件与考核.md`，来源是仓库里的 `晋升.xlsx`。

- 拓展只走拓展表。营运只走营运店端表。营拓要同时过拓展侧和店端侧。
- 资料准确度、完整度按 100%，允许申诉不超过 2 次。
- 营运 Y4-2、Y4-3、Y5，以及拓展 L9 及以上、营拓 L10 及以上，提报项是「联系所在分公司总经理」，由负责人评估，演示数据不能把它判成已满足。
- 评估会读任职日期、技能认证、学习状态（课程完成记为「待认证」）和 `DemoFacts` 里的业务开关。单位、周期或范围对不上时，不把数字算成已满足。
- 提报前必须先把目标岗位设为发展目标。已有另一条提报时，要先取消。
- 考察流程在通过负责人评估前，后面的节点保持锁定。转营拓且当前已是中高职级时，负责人评估之后还要补营拓主管档的前置技能。

`src/promotion.ts` 和 `src/promotion-data.json` 保留早期从《拓展晋升标准》抽出的 7 条相邻职级规则，以及按单位、周期、范围比较业务指标的函数。页面上的提报文案以 `promotion-standards.ts` 为准。

## 演示数据存在哪里

`src/logic.ts` 用 `localStorage` 键 `goodme.career-map.demo.v6`，结构版本是 9。写入失败时页面会提示刷新后修改可能丢失。

读回时会丢掉不存在的岗位、技能和计划状态，并把旧技能 ID 映射到现在的 `skill-y1` 这类 ID。版本低于 9 的存档会按当前岗位应掌握的代码裁掉多出来的认证。恢复默认或全部重置会回到 `initialData()`：每个岗位一名虚拟员工，当前岗位技能已认证，部分岗位的任职日期和业务事实被设成「只差在岗时长」或稳定的通过 / 未通过组合，方便直接看评估差异。

`Employee`、`SkillRecord`、`Plan`、`Metric` 是以后接真实员工、认证、发展计划和业务指标时的数据边界。替换数据源时保留岗位 ID（如 `0-5`、`1-6`、`2-8`）和技能 ID，身份、认证和业务数字分开接。

## 资料从哪来

页面不展示文件名和单元格。出处留在代码、JSON 和下面这些说明里。

| 内容 | 现在用什么 | 出处 |
| --- | --- | --- |
| 岗位名称与年薪 | `src/data.ts` 里的网格 | 开发 Prompt 转录的截图表，并与《营拓职级体系及26年拓展绩效解读-TOBP.pdf》第 14 页核对。原截图未随仓库提供。年薪单位是万元/年，保留「+」、区间和「暂未提供」。 |
| 当前职责 | `src/data.ts` 的 `currentDuties`，阅读版见 `position-duties.md` | 按现岗职责整理，覆盖全部 29 个岗位。 |
| 岗位定位与早期职责摘录 | `src/position-details.json`，14 个低中职级 | 《营运拓展营拓技能清单-TO庚涛.xlsx》「技能清单」表。L8 及以上不从该表覆盖。展示职责以 `currentDuties` 为准。 |
| 技能定义、课程、认证方式 | `src/source-data.json`，21 项技能、50 条必备要求 | 同一工作簿。「技能清单」决定岗位和代码的对应；「认证方式」只补课程和验证标准；分路径明细表只补评估方式，不决定岗位需要哪些技能。 |
| 岗位应掌握代码 | `src/position-skill-codes.ts` | 见 `position-skill-codes.md`。同一序列向上继承，高职级没有新矩阵时不另造代码。 |
| 提报与考察 | `src/promotion-standards.ts` | `晋升.xlsx`。拓展、营拓的拓展侧取「拓展晋升提名及晋升成功标准」；营运、营拓的店端侧取「营运技能提名门槛」。 |
| 早期相邻规则 | `src/promotion-data.json`，7 条 | 《拓展晋升标准-TO庚涛.xlsx》Sheet1。营拓条目标成未最终确认。 |

重新抽取需要本机放上对应 Excel，并安装 Python 与 `openpyxl`：

```bash
python3 scripts/extract_sources.py          # 技能与岗位要求 → src/source-data.json
python3 scripts/extract_position_skills.py  # 岗位技能描述 → src/position-skills.json
python3 scripts/extract_positions.py        # 低中职级定位 → src/position-details.json
python3 scripts/extract_promotion.py        # 早期晋升规则 → src/promotion-data.json
```

脚本默认读取项目根目录下的《营运拓展营拓技能清单-TO庚涛.xlsx》和《拓展晋升标准-TO庚涛.xlsx》。这两份原件和 PDF 没有放进仓库。抽完要再跑 `npm test`，确认岗位代码和提报文案仍与页面规则一致。`晋升.xlsx` 已在仓库中，当前提报标准是按它整理进 `promotion-standards.ts` 的，不是由 `extract_promotion.py` 生成。

`src/source-data.json` 的 `rawMatrixRows` 现为空数组。早期说明里的 35 项技能、278 条职级要求和 519 个矩阵单元格已经不再是当前数据。空白、`/` 和 `0` 不再被脚本收成要求；未编码的通用能力也不再补造代码。

## 待确认，且不在页面上做正式资格判断

`src/data.ts` 的 `issues` 记录口径冲突和当前展示假设。这些条目没有单独画在「演示数据」页上。

- 营拓职级有两种说法：一种是 L8 龙门、L9 大区，另一种是 L9 龙门、L10 大区经理。地图按现在的岗位名称和职级号排列，不把技能按职级整表平移。
- 带教考察周期在 PDF 第 25–26 页和晋升表之间不完全一致，不自动套用相邻岗位规则。
- 资料准确度正文是 100%，同表备注有过渡期 90%。演示按 100% 比较，不把过渡期写成永久标准。
- 加盟商能力在不同表里出现过 Y 编码和 S 编码。现在保留 S 编码，逐项映射仍待核对。
- 地图展示年薪参考区间。其他材料里的测算还包含绩效收入。
- 部分 L8 以上岗位没有可直接对应的技能矩阵，沿用该序列已经列出的代码，不补写高职级细则。
- 转营拓的具体评审条件仍按「不跨三个角色大类」展示。认证组合和评审口径待确认。

未确认的规则只影响展示和演示评估，不产生正式晋升资格。

## 测试覆盖什么

`npm test` 跑 `src/*.test.ts`，不启动浏览器。主要锁住这些约定：

- 每个岗位都有当前职责；默认员工正好持有该岗位应掌握的技能，不多也不少。
- 存档隔离、非法 JSON 回退、过期技能 ID 清理。
- 同序列 1–2 级、跨角色只进第一级、转营拓不跨角色大类，以及三条例外和一条禁止。
- 技能进化能配上当前岗位的上一项；没有上一项时标明是新技能。
- 每条可达晋升都有完整提报条件；两级晋升会带上中间档的前提。
- 营运先认证再提报，拓展侧课程完成即可提报、认证与考察同步。
- 业务指标只有单位、周期、范围一致才比较。
- 能力图三轴按各序列的技能阶梯计点。
